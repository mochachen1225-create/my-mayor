# 1. 發想與企劃

## 發想：先討論，不要急著寫程式
作者通常先丟一個感覺（例如「我推的市長」：玩家當競選總幹事、老闆是抽到的）。先一起把這些想清楚：

- **玩家扮演誰？**選一個有趣的視角，通常是幕後的人，而不是主角本人（總幹事比市長好玩）。
- **一局多久？**手機網頁遊戲 10 分鐘左右最剛好，玩完會想再來一局。
- **核心循環**：例如「突發事件 20 秒決定」＋「沒事時自己排行程」＋「每月民調回饋」。
- **隨機性**：角色隨機抽、事件隨機、空檔隨機，每局才會不一樣。上一局遇過的事件要降低再出現的機率。
- **角色不聽話**：信任值決定角色配不配合，比「玩家說什麼就是什麼」有趣很多。
- **多結局＋分享**：主角結局＋玩家自己的結局（例如總幹事結局），結局要有一句好笑的分享用語。
- **時間點**：季節性、時事型的題材要對準真實日期（例如真實投票日），上架和宣傳都繞著那天排。

## 內容寫法
- 事件、台詞用台灣繁體中文；社群網站寫「脆」，英文版叫 Crisp。
- 現實事件只取「類型」改編：例如「老鼠上新聞」「颱風要不要放假」「小編用錯帳號」。
- 每個角色的槽點強度要一樣，都要有好結局和壞結局，勝率要接近。
- 做壞事的選項一定會在後面爆開，但文字不要預告，也不要在括號裡暴雷。
- 結果文字要具體、有畫面，避免「效果不錯」這種空話。作者會逐句挑剔用詞，照改就好。

## 企劃文件（新 repo 一開始就建）
- `docs/game-design.md`：概要、鐵律、世界觀、角色、時間軸、數值、回合結構、判定流程、內容、介面流程、結局、分享、平衡數據、檔案結構。
- `NOTES.md`：目前進度、設計決定（以及為什麼）、還沒做的想法、更新紀錄（最新的放最上面）。
- `README.md`：給玩家和路人看的介紹、玩法、聲明（純屬虛構）。
- `CLAUDE.md`：給之後接手的 Claude 看的規則，包括「每次修改都要做」和「內容鐵律」，可以直接照 SKILL.md 那份改寫。

## 跟作者溝通
- 回答要簡潔，不要每則都塞一句總結。
- 作者想不出貼文怎麼寫時，不要直接給成品，先問 3、4 個簡單問題（為什麼做、做的時候什麼事讓你笑、朋友怎麼說），用作者自己的回答組成貼文。
- 作者覺得文案像廣告或像 AI，通常是因為：在列功能、每篇都有行動呼籲、太工整、反差句型（本來…結果…）。改成講一件具體的小事、句子不用太完整、不要求留言。
