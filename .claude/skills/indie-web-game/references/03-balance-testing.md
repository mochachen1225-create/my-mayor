# 3. 平衡模擬與測試

## 平衡模擬（每次改規則都要跑）
在 Node 用 `vm` 載入 `data.js`＋`engine.js`（把 `^const ` 換成 `var `，拿掉 `module.exports` 那行），用固定種子跑三種策略，每種角色各 400 局：

- **random**：完全亂選（勝率參考 15～35%）
- **casual**：60% 亂選、40% 選期望值最高的（勝率目標 50～65%，各角色要接近）
- **mixed**：35% 亂選（勝率參考 70～80%）

模擬也要模仿 UI 的強制規則（例如體力低時強制休息、歸零倒下），不然數字會失真。

每次都要看兩件事：
1. **各角色勝率**有沒有偏掉（差距太大就調起始值或角色專屬事件）。
2. **結局分布**：輸出每種角色前 40 名「結局｜玩家結局」組合，看稀有結局有沒有變得太常見。稀有度標準：≥3% 普通、0.5～3% 稀有、<0.5% 傳說。

經驗：
- 加新選項要小心「沒有風險又一定配合」的選項，會讓勝率暴增（我們的小遊戲一開始讓勝率從 55% 衝到 75%）。
- 新機制常讓某個結局爆量，要嘛收緊條件（例如「最後一週又倒下」＋「倒下兩次以上」），要嘛改稀有度。
- 用同一組種子比較新舊版本，任何差異都來自你的修改。

## 手機實測（Playwright）
雲端環境有預裝 Chromium 和 Playwright，`require('playwright')` 就能用，不要重新安裝。

- viewport 390×844、deviceScaleFactor 2。
- 用 `addInitScript` 先設好 localStorage（語言、音效關、版本號），避免跳出新版提醒。
- 腳本自動點：有選項就點、有「繼續／開工」就點、行程板點第一個（或優先點要測的功能，例如小遊戲）、小遊戲就實際去點冒出來的格子。
- 記錄 `pageerror` 和 console error，最後印出來，要是空的。
- 英文版要掃描整個畫面的文字，找殘留的中文和沒被代入的 `{placeholder}`。
- 要測分享截圖時，用 `python3 -m http.server` 開本地伺服器；`file://` 會讓 canvas 被污染，無法輸出圖片。
- 截幾張關鍵畫面，拼成一張縮圖自己看（PIL 拼圖），確認版面沒跑掉。

## 回報 bug 的處理
作者或玩家回報 → 先讀程式找出真正原因（不要猜）→ 修 → 版本號＋CHANGES（寫「感謝玩家回報」）→ 模擬＋實測 → 重新打包 → 推上去 → 通知總編。
